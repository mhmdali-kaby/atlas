# ATL-112: Market Scout's replay evals

Builds on the ATL-92 harness (`docs/handoff/ATL-92-eval-harness.md`). There are 30 cases in
`services/agents/evals/market_scout/`, generated by `build_cases.py` in that folder. Tests are in
`services/agents/tests/test_market_scout_evals.py`.

## Running them

```sh
cd services
uv run python -m atlas_agents.evals run --agent market_scout --fake   # scripted answers, no CLI
uv run python -m atlas_agents.evals run --agent market_scout          # real Claude CLI login (owner)
uv run python agents/evals/market_scout/build_cases.py                # regenerate every case
```

`baseline.json` comes from **`--fake` mode** (`"mode": "fake"`): 30 cases, 133 properties, 100%.
It shows that the harness and the code rules work. It does not measure the model. The real-CLI
baseline is the owner's to run (handover): run without `--fake`, then copy
`evals/results/market_scout/<stamp>.json` over `baseline.json`.

## How a Scout case runs (the part you can't get from case.yaml)

The default driver sends `case.prompt` to the supervisor. Market Scout has its own driver,
`atlas_agents/evals/drivers.py:market_scout_driver`, which runs the real
`run_watchlist(host, trigger="eval", day=owner_day(replay_as_of), replies_from=...)`:

- The **feature table** is the snapshot's `research_reports` row (`kind: feature_table`, with
  `valid_until` after the replay time). `prepare()` reuses it, so the shortlist, the pre-score, the
  correlation flags (from the snapshot's 1D `candles`) and the prompt are all built by production code.
- **Teammate replies** come from `inputs.replies` in case.yaml, through the new
  `run_watchlist(..., replies_from=)` parameter. A teammate missing from `inputs.replies` times
  out, which gives `partial_evidence`. Nothing waits 300 s.
- The **transcript** is the code-posted watchlist card with the runtime keys removed (ids, clock,
  version, evidence, meta), plus its `content_md`. Numbers are checked against the run's tool
  outputs, the inputs table the prompt showed, the replies, and the picks' own rank and conviction.
  Rank and conviction are judgments, not data.
- The fake client answers **one** query. A fake answer that the reviewer refuses (schema or
  correlation follow-up) ends the case with `ScriptExhaustedError`, so scripts must be valid the
  first time.

`EvalCase` gained an optional `inputs: {}` field that the agent's driver reads. Register another
agent's driver in `drivers.DRIVERS`.

## Snapshot loader changes

- A table that is not an `atlas_shared.db` model is reflected from the DB. That covers `settings`
  and `settings_history`, which every Scout case needs: the Scout prompt needs `MAX_PICKS`, and in
  replay it reads `settings_history`.
- `settings` replaces the env's row instead of adding a second one.
- Tables load parents first (`watchlists` before `watchlist_items`), not in file-name order.

## Properties added (`evals/properties.py`)

`valid_watchlist`, `rejected_listed {count}`, `picks_count {min,max}`,
`no_trade_day {max_picks, max_conviction}`, `max_conviction {max}`, `picked {inst_ids}`,
`not_picked {inst_ids}`, `max_correlated {groups, max}`, `asset_classes {min}`. The card status is
checked with `verdict_in {field: status, values: [...]}`.

## Categories (case id prefix → category property)

| prefix | cases | asserts |
| --- | --- | --- |
| `mixed_` | 6 | `asset_classes min 2`, status `published` |
| `notrade_` | 5 | `no_trade_day max_picks 1, max_conviction 0.5` |
| `chasing_` | 4 | the > 3 ATR mover is `not_picked` |
| `correlated_` | 4 | `max_correlated max 2` (the candles give corr > 0.9 inside the group) |
| `timeout_` | 4 | status `partial_evidence`, `max_conviction 0.5`; the script asks for more than 0.5 so code does the capping |
| `owner_` | 4 | the pin is `picked`; removed and blocklisted instruments are `not_picked` |
| `single_` | 3 | the momentum-only instrument is `not_picked` |

Every case also asserts `valid_watchlist`, `no_invented_numbers` and `rejected_listed count 3`.

## Not done here

- The production reviewer's number guard (`card.meta`) still counts a pick's conviction as a
  number with no tool source unless it matches one by chance. The eval adds convictions to the
  pool, but production does not. A side effect in the eval: each pick's rank and conviction are
  in the numguard pool (`drivers.py`), so a thesis number that happens to equal one (e.g. 0.65)
  counts as sourced. Accepted for now; tighten it when production's guard learns about convictions.
- `baseline.json`'s `baseline.path` was hand-edited to the repo-relative path; the runner still
  writes absolute paths into new result files.
- No case covers the news-down class cap or an empty shortlist (where the model is never called).

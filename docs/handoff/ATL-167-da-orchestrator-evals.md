# ATL-167 — Devil's Advocate and Orchestrator replay evals (brief §7.7, §7.9, §7.11)

## Two-minute version

- 31 cases under `services/agents/evals/devils_advocate/`, 33 under `services/agents/evals/orchestrator/`,
  each folder generated by its `build_cases.py` (run from `services/`:
  `uv run --package atlas-agents python agents/evals/<agent>/build_cases.py`). Edit the generator, not the
  case files; regenerating is byte-stable.
- `baseline.json` in each folder is the fake-mode run (100 %). Real runs:
  `uv run --package atlas-agents python -m atlas_agents.evals run --agent devils_advocate` (or
  `orchestrator`); `--dry-run` lists the cases with no CLI and no DB; `--fake` replays the scripts.
- pytest: `agents/tests/test_devils_advocate_evals.py` and `agents/tests/test_orchestrator_evals.py`
  (counts, category properties, the whole fake run, planted bad answers, dry run).

## Drivers (`atlas_agents/evals/drivers.py`)

`devils_advocate` — `inputs.mode`:

- `review` (default): `devils_advocate.review(proposal_id, message_id)`; the code table is built from the
  snapshot's candles, events and positions. Transcript card = the posted `da_review` without
  `precomputed` / `corrections` / `meta` (those go to `Transcript.meta`).
- `rerate`: each `inputs.replies[]` (`{reply_to: <stored row id>, content_md}`) goes through the
  production hook `on_strategist_reply`, then `settled()`. `meta.rerate_cards` and `meta.model_runs` count
  what happened. The driver clears the hook's in-process `_rerated` key for the case's proposal first, so
  re-running a case starts clean.
- A card code rejects (e.g. a missing item) cannot be retried by a one-answer fake script; the driver
  records the reviewer's reasons and appends them to the run error:
  `…; card rejected: checklist items missing: 4 (stop_quality); …`.

`orchestrator` — `inputs.mode`:

- `owner` (default): `inputs.message` goes through `why.answer_why` (for `/why <id>`) or
  `owner.handle_owner_message` + `owner.route` for non-decisive kinds. The hook itself
  (`take_owner_message`) returns early while replaying, so the driver calls these directly.
- `loop`: `inputs.replies[]` are fed to `loops.observe` as War Room messages; a hit goes to `loops.stop`.
  `loops.reset()` runs before and after.
- `meta` holds every posted message (bus + the run's final `RunResult.message`), code and final
  classification, the model's routing, assignments, and settings version / proposal statuses before and
  after. The `/why` "Cards: …" line and the card's `links` are code's, so they are left out of the text
  and card the number guard reads (`why_answered` checks them from `meta.posted`).

## Properties (`atlas_agents/evals/properties.py`)

DA: `checklist_complete`, `rating_follows_guide {expected}`, `item_flagged {item, min_severity, patterns,
precomputed: events|stop_noise}`, `no_false_alarm {max_rating}`, `rerated_once {expected, rerate_of}`.
Orchestrator: `classified_as {expected, code, reply_to, assign}`, `limit_refused {setting, section}`,
`why_answered {max_words, min_links, inst_id, model}`, `no_silent_approval {awaiting}`,
`loop_stopped {expected, agents, replies, proposal_id}`.

`no_silent_approval` strips negated phrases ("silence is never taken as approval", "not an approval")
before looking for an approval claim, and also fails on a proposal status change, an assignment to
approve/execute/place, or a model kind of `approval` on a message code did not classify as one.

## Worth knowing

- `window_events` reads every `economic_events` row in the window (no env filter). Cases sit in April
  (DA) and May (Orchestrator) 2026 with events created two days before, so leftovers from other tests
  are unlikely to leak; `no_false_alarm` also fails if the "clean" table shows an event.
- Limit changes, approvals and loop stops never reach the model, so those cases script an unused answer
  and assert `model_ran` is false where it matters.
